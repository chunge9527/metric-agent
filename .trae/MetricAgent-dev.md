# MetricAgent 技术方案详细文档

**文档版本**：V1.1 **适用版本**：Go 1.25.0 + Nacos Server 2.5.3 **文档状态**：正式版 **对应 PRD**：MetricAgent 产品需求文档

### 版本变更摘要（V1.0 → V1.1）

1. **移除 lumberjack 依赖**：日志文件轮转改为自研 `DailyRotator`，按本地时区午夜自动轮转，`cleaner.go` 按保留天数清理历史文件
2. **修复 guardian 巡检统计**：`componentStartSuccess` case 不再错误递增 `hcFail++`，自愈成功不再被双记为健康检查失败
3. **修复日志轮转时区**：`dailyCheckLoop` 从 UTC 午夜截断改为本地时区午夜计算，适配中国等非零时区部署
4. **Shell 输出限流**：新增 `cappedWriter`，stdout/stderr 单流上限 1MB，防止脚本输出大量数据导致 OOM
5. **Shell 执行日志降级**：成功日志从 INFO 降为 DEBUG 且不再打印完整脚本内容；非零退出码从 ERROR 降为 WARN
6. **runReloadScript 日志截断**：stdout/stderr/script 在日志中截断到 5KB 预览，防止敏感信息泄漏和日志爆炸
7. **端口检测错误匹配**：从脆弱字符串匹配改为 `errors.Is(syscall.EADDRINUSE)` + `errors.As(*net.OpError)` 跨平台检测
8. **优雅关闭强制连接关闭**：AfterFunc 超时时调 `SetKeepAlivesEnabled(false)` 阻止新连接进入
9. **守护 ips 127.0.0.1 自动过滤**：配置中若包含 127.0.0.1 自动剔除，全部过滤则标记配置无效
10. **请求透传无 SSRF 防护**：内网部署场景移除了 SSRF 防护（原设计含 CIDR 私有网段检查），允许访问内网任意 http/https 服务

## 一、项目概述

### 1.1 项目背景

随着监控集群规模扩大，节点侧 VictoriaMetrics、Promxy 等监控组件的运维面临配置分散、脚本零散、进程无守护、运维操作不安全等问题。MetricAgent 作为部署于监控节点的轻量级运维代理，提供统一的配置分发、组件生命周期管理、进程自愈、远程命令执行、请求透传、定时任务能力，实现监控节点的标准化远程运维，降低运维成本，提升操作安全性与可靠性。

### 1.2 建设目标

1. **功能目标**：100% 覆盖 PRD 定义的两种运行模式、六大核心能力，满足监控节点运维全场景需求。
2. **交付目标**：单二进制文件交付，无外部依赖，拷贝即可部署，适配主流 Linux 系统与 CPU 架构。
3. **性能目标**：接口响应、配置同步、调度精度满足 PRD 性能指标，资源占用极低。
4. **可靠性目标**：单个模块异常不导致主进程崩溃，全链路容错，支持配置回退与断连降级。
5. **安全目标**：全接口鉴权、远程命令加密传输、操作权限可控，保障运维安全。

### 1.3 需求范围

表格

| 需求分类 | 包含内容                               | 对应 PRD 章节 |
| ---- | ---------------------------------- | --------- |
| 运行模式 | HTTP 服务模式、指令执行模式，模式互斥              | 第二章       |
| 配置管理 | Nacos 配置对接、二级配置拉取分发、原子写入、备份回滚、变更监听 | 3.2 节     |
| 指令执行 | 远程加密 Shell 执行、本地指令单次执行、超时控制        | 3.3 节     |
| 进程守护 | 健康检查、自动拉起、重试机制、熔断机制                | 3.4 节     |
| 请求透传 | HTTP 全类型请求转发、地址校验、超时控制             | 3.5 节     |
| 定时任务 | Cron 调度、PromQL 查询、文件输出、自动滚动        | 3.6 节     |
| 安全鉴权 | 全接口鉴权、双请求头支持、大小写敏感匹配               | 3.7 节     |
| 可观测性 | 结构化 JSON 日志、分级输出、文件轮转              | 第五章       |

## 二、技术选型与版本稳定性论证

### 2.1 开发语言选型

**选型**：Go 1.25.0，`CGO_ENABLED=0` 纯静态编译

#### 选型理由

1. **单文件交付匹配**：Go 原生支持静态编译，关闭 CGO 后生成无系统依赖的单个二进制文件，完美匹配 “拷贝即部署、无需额外安装” 的产品要求。
2. **并发性能**：原生 goroutine 并发模型轻量高效，千级 goroutine 内存占用仅 MB 级，适配后台常驻代理的多任务场景；标准库 HTTP、加密、进程管理能力性能优异。
3. **跨平台兼容**：原生支持交叉编译，可直接生成 Linux amd64/arm64 架构产物，覆盖 CentOS、Ubuntu、Debian 等主流发行版。
4. **供应链安全**：标准库覆盖 80% 以上核心能力，第三方依赖极简，降低供应链风险与维护成本。

### 2.2 核心依赖组件选型

所有依赖均采用生产级稳定版本，与目标环境完全兼容，无已知严重缺陷。

1. **轻量性**：全链路依赖均为小型纯 Go 库，编译后二进制体积可控，符合 “轻量级运维代理” 定位。
2. **稳定性**：所有依赖均经过大规模生产环境验证，无已知严重 Bug，版本锁定避免非预期升级。

4. **可维护性**：基础设施层全部抽象接口，后续替换组件不影响业务层代码，可扩展性强。

## 三、整体架构设计

### 3.1 设计原则

1. **单一职责原则**：每个模块仅负责一项核心功能，职责边界清晰，便于开发与测试。
2. **依赖倒置原则**：核心业务层依赖抽象接口，不依赖具体实现，便于单元测试与组件替换。
3. **高内聚低耦合**：同模块内逻辑高度聚合，模块间通过接口交互，降低耦合度。
4. **最小依赖原则**：优先使用标准库，严格控制第三方依赖数量与版本。
5. **故障隔离原则**：单个模块异常不影响主进程与其他模块运行，具备降级与熔断能力。
6. **可观测原则**：全链路结构化日志，关键操作与异常均可追溯。

### 3.2 五层分层架构

采用自顶向下的依赖倒置设计，上层依赖下层抽象接口，不依赖具体实现，整体架构如下：

表格

| 层级          | 核心职责                             | 包含模块                                     |
| ----------- | -------------------------------- | ---------------------------------------- |
| **入口层**     | 命令行参数解析、运行模式策略分发、系统信号监听、进程生命周期管理 | main.go、优雅关闭模块                           |
| **核心服务层**   | 业务逻辑编排，调用基础设施能力完成业务目标，仅依赖抽象接口    | 配置分发服务、指令执行服务、进程守护服务、请求透传服务、定时任务服务、鉴权中间件 |
| **基础设施接口层** | 定义外部依赖的抽象接口，隔离业务与实现，是依赖倒置的核心     | 配置中心接口、Shell 执行器接口、加解密接口                 |
| **基础设施实现层** | 封装第三方 SDK 与系统能力，实现接口层定义的能力       | Nacos 客户端实现、Shell 执行器实现、AES 加密实现         |
| **公共模型层**   | 全局数据结构定义、通用工具、统一日志、错误规范          | 配置结构体、API 模型、文件工具、日志、常量、错误码              |

### 3.3 核心设计模式应用

所有设计模式均为工程化优化，不新增 PRD 外业务需求，核心目标是提升代码可维护性、可测试性与健壮性。

表格

| 设计模式       | 应用场景              | 解决的问题                                          | 业务价值                      |
| ---------- | ----------------- | ---------------------------------------------- | ------------------------- |
| **策略模式**   | 运行模式分发            | HTTP 服务模式与指令执行模式逻辑解耦，新增模式无需修改主入口代码             | 符合开闭原则，扩展运行模式成本低          |
| **观察者模式**  | Nacos 配置变更通知      | 配置变更触发配置分发、监听列表更新等多个下游动作，解耦配置源与业务处理            | 新增配置变更消费方无需修改 Nacos 客户端代码 |
| **模板方法模式** | 二级配置分发流程          | 统一「拉取→写入临时文件→备份→原子重命名→执行重载脚本」的标准流程，消除重复代码      | 统一失败重试与回滚逻辑，避免各配置项处理不一致   |
| **状态机模式**  | 进程守护熔断机制          | 清晰定义「正常→失败计数→熔断中→恢复正常」的状态流转规则，替代零散的 if-else 判断 | 逻辑清晰，避免边界条件错误，便于扩展熔断等级    |
| **中间件模式**  | HTTP 鉴权           | 鉴权逻辑与业务接口解耦，除 `/api/v1/exec` 外全接口统一拦截 | 鉴权逻辑集中维护，业务接口无感知          |
| **单例模式**   | 全局配置、日志、Nacos 客户端 | 全局唯一实例，避免重复初始化与资源浪费                            | 资源占用低，状态一致                |

### 3.4 核心运行流程

#### 3.4.1 启动总流程

1. 解析命令行参数，优先处理`--help`参数，存在则输出用法说明并以 0 码退出。
2. 运行模式互斥校验，根据参数选择对应运行策略。
3. 初始化基础配置与日志组件（指令模式仅初始化控制台日志）。
4. 注入基础设施层实现，启动对应运行模式。
5. 注册系统信号监听，等待进程退出信号，触发优雅关闭。

#### 3.4.2 HTTP 服务模式运行流程

1. 加载并校验基础配置`metricAgent.yml`，校验`agent_id`必填字段与格式。
2. 初始化 Nacos 客户端：启动阶段连接失败按 60 秒间隔重试，不阻塞主进程启动。
3. 拉取配置清单：优先拉取节点个性化配置，不存在则拉取公共配置作为兜底。
4. 注册配置清单变更监听，同时监听清单中所有二级配置项的变更。
5. 串行执行全量二级配置分发，完成文件写入与重载脚本执行。
6. 启动后台守护协程：进程守护巡检、定时任务调度。
7. 注册 HTTP 路由与鉴权中间件，启动 HTTP 监听服务。
8. 进入常驻运行状态，等待系统信号。

#### 3.4.3 指令执行模式运行流程

1. 读取`--exec`脚本字符串或`--exec-file`指定文件内容，解析`--`分隔符后的参数。
2. 仅初始化控制台日志，不创建日志文件，不加载任何配置文件。
3. 同步执行 Shell 脚本，捕获标准输出、标准错误与退出码。
4. 将脚本标准输出打印到 stdout，错误信息打印到 stderr。
5. 以脚本退出码作为进程退出码，执行完成直接退出。

## 四、核心模块详细设计

### 4.1 入口与运行时模块

#### 4.1.1 功能定位

程序主入口，负责命令行参数解析、运行模式策略分发、系统信号监听与优雅关闭。

#### 4.1.2 命令行参数设计

表格

| 参数            | 所属模式      | 默认值                      | 规则说明                       |
| ------------- | --------- | ------------------------ | -------------------------- |
| `--help`      | 通用        | -                        | 最高优先级，存在则输出完整用法说明后以 0 码退出  |
| `--exec`      | 指令执行模式    | -                        | Shell 脚本字符串，与 HTTP 模式参数互斥  |
| `--exec-file` | 指令执行模式    | -                        | Shell 脚本文件路径，与 HTTP 模式参数互斥 |
| `--port`      | 指令执行模式    | `9092`                   | 目标 HTTP 服务端口，指令模式向 `127.0.0.1:port` 发 AES 加密请求 |
| `--timeout`   | 指令执行模式    | 服务端 60 秒                   | 执行超时秒数，客户端上限 1800 秒，0 表示使用服务端默认值 |
| `--config`    | HTTP 服务模式 | `./metricAgent.yml`     | 基础配置文件路径，支持绝对 / 相对路径（相对二进制目录） |
| `--bind-addr` | HTTP 服务模式 | `0.0.0.0:9092`           | HTTP 服务监听地址                |
| `--logs`      | HTTP 服务模式 | `./logs/metricAgent.log` | 日志文件路径（相对二进制目录）           |

> **模式互斥校验**：代码同时支持"指令模式混入 HTTP 参数"和"HTTP 模式混入指令参数"的双向检测，任一类参数混入另一模式立即报错退出。

#### 4.1.3 核心逻辑

1. **参数解析**：使用标准库`flag`包解析，自定义`--`分隔符处理逻辑，分隔符后内容原样作为脚本参数。
2. **互斥校验**：同时传入指令模式参数与 HTTP 模式参数时，直接输出错误并以非 0 码退出。
3. **路径基准统一**：所有相对路径均以**二进制可执行文件所在目录**为基准，通过`os.Executable()`统一获取，避免工作目录不同导致的路径错误。
4. **直接函数分发**：根据参数选择调用 `runExecMode` 或 `runHTTPMode`，无抽象 Runner 接口。

#### 4.1.4 优雅关闭设计

1. **信号监听**：监听`SIGINT`、`SIGTERM`系统信号。
2. **关闭顺序**：
   1. 停止 HTTP 服务，拒绝新请求，等待正在处理的请求完成。
   2. 停止定时任务调度器，等待运行中的任务执行完成。
   3. 关闭 Nacos 连接，取消所有配置监听。
   4. 刷写日志缓冲区，关闭日志文件。
3. **强制退出保护**：设置 10 秒强制退出超时，超时未完成则强制退出，避免进程挂死。

### 4.2 启动引导模块

#### 4.2.1 配置加载器（config_loader.go）

**功能**：加载、解析、校验基础配置文件，填充默认值。 **核心逻辑**：

1. 路径解析：相对路径基于二进制目录拼接，支持绝对路径。
2. 文件读取与 YAML 解析。
3. 必填校验：`agent_id`为必填字段，仅允许字母、数字、下划线、横线，通过正则校验。
4. 默认值填充：补全所有超时时间、端口、重试间隔等配置的默认值。 **异常处理**：文件不存在、格式错误、必填字段缺失时，输出精准错误信息，进程直接退出。

#### 4.2.2 服务初始化器（server_init.go）

**功能**：依赖注入、组件初始化、HTTP 服务注册启动。 **核心逻辑**：

1. 初始化基础设施层实现（Nacos 客户端、Shell 执行器、加密工具）。
2. 初始化核心服务层实例，通过构造函数注入依赖接口。
3. 注册 HTTP 路由与鉴权中间件。
4. 启动后台守护协程。
5. 启动 HTTP 监听服务。

### 4.3 配置管理服务（ConfigService）

#### 4.3.1 功能定位

对接 Nacos 配置中心，实现配置拉取、变更监听、二级配置分发、原子写入、备份与回滚，是配置自动化的核心模块。

#### 4.3.2 配置拉取优先级与回退策略

严格遵循 PRD 定义的优先级规则：

1. 优先拉取个性化配置 `metricFileConfig-{agent_id}.yml`。
2. 若个性化配置不存在、拉取失败或内容为空，则尝试拉取公共配置 `metricFileConfig.yml` 作为兜底。
3. 运行过程中，若个性化配置被删除或置空，自动回退到公共配置。
4. 两个配置完全独立，互不影响。

#### 4.3.3 配置分发模板流程

采用模板方法模式，单条配置项统一执行以下流程，串行依次处理：

```
1. 从Nacos拉取对应dataId的配置内容
2. 写入同目录下临时文件（.tmp_前缀）
3. 若目标路径已存在同名文件，备份为 {文件名}_agent_bak
4. 原子重命名临时文件为目标文件名
5. 执行配置对应的reloadScript重载脚本

```


#### 4.3.4 核心机制

1. **原子写入机制**：
   * 先写入临时文件，写入完成后调用`os.Rename`原子替换目标文件（Linux 下为原子操作）。
   * 避免写入过程中程序异常导致配置文件损坏。
2. **备份机制**：
   * 替换前若目标文件已存在，重命名为`{reFileName}_agent_bak`，与原文件同目录。
   * 多次更新直接覆盖旧备份，保留最近 1 个有效版本。
3. **失败重试与回滚**：
   * 单步骤（拉取 / 写入 / 重命名 / 脚本执行）失败，立即重试 1 次。
   * 重试仍失败：记录错误日志 → 恢复备份文件（无备份则删除新写入的文件） → 跳过当前配置项，继续执行下一条。
   * 单条配置处理失败不中断其他配置项执行。

#### 4.3.5 配置变更监听

1. 长连接监听当前生效的配置清单（个性化或公共）。
2. 自动监听清单中所有二级配置的`dataId`；清单变更时，动态新增 / 移除监听项。
3. 配置变更事件触发后，执行全量配置分发流程。

#### 4.3.6 Nacos 重连策略

严格区分启动阶段与运行阶段，符合 PRD 要求：

* **启动阶段**：Nacos 连接失败，打印错误日志，每隔 60 秒尝试重连，不影响主进程启动。
* **运行阶段**：检测到连接断开，每隔 30 秒重试一次，加快恢复速度。

### 4.4 指令执行服务（CommandService）

#### 4.4.1 功能定位

提供两种指令执行能力：HTTP 远程加密命令执行、本地指令单次执行，统一封装 Shell 执行底层能力。

#### 4.4.2 Shell 执行器基础设施封装

**接口定义**：

```
type ShellExecutor interface {
    Exec(ctx context.Context, script string) (stdout string, stderr string, exitCode int, err error)
}

```


**实现逻辑**：

* 基于标准库`os/exec.CommandContext`实现，通过`context.Context`控制超时。
* 超时后自动终止子进程，避免僵尸进程。
* 执行权限与工作目录与 Agent 进程一致。
* 捕获标准输出、标准错误与进程退出码。

#### 4.4.3 HTTP 远程执行模式

1. **接口**：`POST /api/v1/exec`
2. **处理链路**：
   1. 鉴权中间件校验通过。
   2. AES 解密请求体，提取脚本内容与自定义超时参数。
   3. 参数校验：拒绝空脚本、纯空白字符脚本；超时默认 60 秒，最大不超过 600 秒，参数非法返回 400 错误。
   4. 调用 ShellExecutor 执行脚本，统计执行耗时。
   5. 封装执行结果（stdout、stderr、exitCode、执行耗时），AES 加密后返回。

#### 4.4.4 本地指令执行模式

1. 读取`--exec`脚本字符串，或读取`--exec-file`指定文件内容。
2. 拼接`--`分隔符后的所有参数。
3. 调用 ShellExecutor 同步执行。
4. 标准输出打印到 stdout，错误信息打印到 stderr。
5. 执行完成后进程直接退出，退出码与脚本退出码一致。
6. 不启用文件日志，不创建任何日志文件。

### 4.5 进程守护服务（GuardianService）

#### 4.5.1 功能定位

定时读取守护配置，对监控组件进行健康检查与异常自愈，具备熔断机制避免无效重试。

#### 4.5.2 熔断状态机设计

采用状态机模式管理组件守护状态，定义 4 种核心状态：

表格

| 状态   | 说明                 | 流转条件                                  |
| ---- | ------------------ | ------------------------------------- |
| 正常   | 组件健康检查通过，失败计数为 0   | 健康检查失败 → 进入失败计数状态                     |
| 失败计数 | 组件异常，执行拉起操作，累计失败次数 | 拉起成功 → 回到正常状态，计数清零连续 3 次拉起失败 → 进入熔断状态 |
| 熔断中  | 停止拉起操作，仅做健康检查与日志记录 | 5 分钟熔断周期结束 → 进入恢复状态                   |
| 恢复正常 | 重置失败计数，恢复自愈逻辑      | 健康检查通过 → 回到正常状态                       |

#### 4.5.3 核心逻辑

1. **配置加载**：每分钟读取`./crontab.yml`，新配置在下一轮巡检周期生效，不中断当前正在执行的任务。
2. **调度防重叠**：通过`sync.Mutex`标记运行状态，上一轮巡检未完成则跳过本轮，记录 WARN 日志。
3. **IP 匹配**：获取本机所有网卡 IP，与组件 `ips` 数组做精确匹配，宿主机任意 IP 命中数组任意一项即执行守护逻辑。
   * **`127.0.0.1` 自动过滤**：若配置的 `ips` 数组中包含 `127.0.0.1`，校验阶段自动剔除并记录 Warn 日志；若剔除后数组为空，则标记该组件配置为无效并跳过守护流程。
4. **健康检查**：
   * 执行`healthCheckScript`，退出码为 0 表示组件存活，非 0 表示不存活。
   * 健康检查默认超时 60 秒，超时直接判定为检查失败，强制终止子进程。
5. **自愈与重试**：
   * 判定组件不存活时，立即执行`startScript`拉起组件。
   * 启动脚本默认超时 120 秒。
   * 拉起后间隔 5 秒重试健康检查（默认 1 次），仍失败则计一次失败。
6. **熔断机制**：
   * 单个组件连续 3 次拉起失败后，进入 5 分钟熔断周期。
   * 熔断期间仅做健康检查与日志记录，不执行拉起操作。
   * 熔断周期结束后自动恢复自愈逻辑，重置失败计数。
   * 熔断状态不持久化，Agent 重启后计数清零。

#### 4.5.4 异常处理

* 配置文件读取失败、格式错误时，记录错误日志，沿用上次有效配置，不中断守护流程。
* 健康检查脚本、启动脚本执行异常，均记录详细错误日志。

### 4.6 请求透传服务（ForwardService）

#### 4.6.1 功能定位

提供 HTTP 请求透传能力，将请求转发至指定目标服务并原样返回响应，支持全类型 HTTP 请求。

#### 4.6.2 接口规则

* 接口路径：`/forward`
* 请求参数：`target`，值为目标服务基础 URL，需经 URL 编码，Agent 侧自动解码。
* 转发规则：实际转发地址 = `target`基础 URL + 原始请求路径 + 查询参数；若`target`已包含查询参数，则目标参数优先级更高。

#### 4.6.3 核心逻辑

1. **地址合法性校验**：
   * 仅允许 http/https 协议。
   * 禁止解析出多个 IP 地址。
   * 不合法则返回 403 Forbidden。
2. **请求构建**：
   * 完整保留原始请求方法、请求头、Cookie、请求体。
   * 移除 Hop-by-hop 头（如`Connection`、`Keep-Alive`等）。
3. **转发控制**：
   * 默认超时 30 秒，最大 120 秒，可在基础配置中调整。
   * 禁止自动跟随重定向，目标返回 3xx 状态码时直接透传给客户端。
4. **响应透传**：原样返回目标服务的响应状态码、响应头、响应体。

#### 4.6.4 异常处理

* 目标服务不可达 → 返回 502 Bad Gateway
* 请求超时 → 返回 504 Gateway Timeout
* 地址解析失败、非法地址 → 返回 403 Forbidden

### 4.7 定时任务服务（ScheduleService）

#### 4.7.1 功能定位

根据配置定时查询 VictoriaMetrics 指标，按规则写入指定文件，支持文件自动滚动。

#### 4.7.2 核心逻辑

1. **配置加载**：加载`./scheduledConfig.yml`，解析任务列表与 Cron 表达式。
2. **任务调度**：
   * 基于`cron/v3`创建调度器，开启`WithPanicRecovery`。
   * 每个任务独立调度，多个任务按配置顺序串行执行。
3. **PromQL 查询**：
   * 按配置串行执行多个 PromQL 查询。
   * 携带配置的`Authorization`请求头访问 VictoriaMetrics，支持从环境变量读取鉴权信息。
   * 单个查询失败记录错误日志，不影响其他查询执行。
4. **结果写入**：
   * 格式化结果为指定 JSON 结构：`{"queryTime":"YYYYMMDDHHmmss","queryKey":"xxx","data":[...]}`。
   * 默认追加写入模式，支持配置覆盖模式。
5. **文件滚动机制**：
   * 触发条件：文件大小超过配置的`maxFile`（单位 MB），或每日 00:00:00。
   * 滚动规则：重命名当前文件为`metricdata.txt_yyyyMMdd`，新建文件继续写入。

### 4.8 鉴权中间件（AuthMiddleware）

#### 4.8.1 功能定位

所有 HTTP 接口强制鉴权（`/api/v1/exec` 免 HTTP 鉴权，仅依赖 AES 加密防护），保障运维操作安全。

#### 4.8.2 鉴权规则

1. 从请求头读取`Authentication`与`CIB-AUTHORIZATION`两个字段。
2. 与配置的密钥进行**大小写敏感的精确匹配**。
3. 任意一个请求头匹配成功，即鉴权通过，放行请求。
4. 两个请求头均不匹配，返回 401 Unauthorized。
5. 除 `/api/v1/exec` 外，所有 HTTP 接口（含透传接口）均强制开启鉴权。

### 4.9 基础设施层实现

#### 4.9.1 Nacos 客户端

* 实现`ConfigCenter`接口，封装 nacos-sdk-go v2.3.5。
* 支持配置拉取、长连接监听、自动重连、监听管理。
* 配置 Nacos 服务地址、命名空间、分组，适配 nacos-server-2.5.3 的 gRPC 通信。

#### 4.9.2 AES 加密工具

* 实现`Crypto`接口，采用 AES-CBC 对称加密算法。
* 加密密钥在基础配置中独立配置。
* 加密范围：远程命令请求体脚本内容、响应体执行结果；鉴权请求头不加密。

#### 4.9.3 Shell 执行器

* 实现`ShellExecutor`接口，封装系统 Shell 执行能力。
* 统一超时控制、输出捕获、退出码返回。

### 4.10 公共工具层

#### 4.10.1 结构化日志

* 基于标准库 `log/slog` 实现，输出 JSON 格式结构化日志。
* 日志级别：DEBUG、INFO、WARN、ERROR 四级。
* 双输出模式：HTTP 模式同时输出到控制台与日志文件；指令模式仅输出到控制台。
* 文件轮转：自研 `DailyRotator`（`logger/rotator.go`），按**本地时区午夜**自动轮转（`time.Date(now.Year(), now.Month(), now.Day()+1, 0,0,0,0, now.Location())`），后台循环用一次性 timer 等待到下一个午夜，比 1s ticker 高效。轮转文件命名 `{prefix}-yyyy-MM-dd.log`。
* 历史清理：`cleaner.go` 后台协程按 `Log.RetentionDays`（可配置）扫描日志目录，删除超过保留天数的历史文件，每天检查一次。
* Shell 输出保护：所有 Shell 执行 stdout/stderr 单流上限 1MB（`MaxShellOutputBytes`），超限时截断并 Warn 标记；日志中 stdout/stderr/script 预览上限 5KB（`ShellLogPreviewBytes`），防止敏感信息泄漏和日志爆炸。

#### 4.10.2 文件工具集

* 原子写、文件备份、目录检查、权限校验等通用文件操作。
* 统一封装，避免重复实现。

#### 4.10.3 统一错误与常量

* 全局错误码定义，统一错误处理规范。
* 全局常量、默认值集中管理。

## 七、非功能需求设计

## 七、非功能需求设计

### 7.1 性能设计

表格

| 指标           | PRD 要求      | 实现保障                                        |
| ------------ | ----------- | ------------------------------------------- |
| 加解密耗时        | 不明显影响命令执行效率 | 标准库 AES 硬件加速，加解密耗时微秒级，对整体执行耗时影响可忽略          |
| 常规 HTTP 接口响应 | <100ms      | 基于标准库`net/http`原生实现，无多余框架开销，简单接口响应耗时 < 10ms |
| 进程守护调度误差     | <5 秒        | cron/v3 调度器调度误差毫秒级，远优于要求                    |
| 单条配置同步耗时     | <2 秒        | 串行 IO + 网络操作，无多余计算，单条配置平均耗时亚秒级              |

### 7.2 可靠性设计

1. **故障隔离**：所有后台任务运行在独立 goroutine 中，通过`recover`捕获 panic，单个模块异常不导致主进程崩溃。
2. **全链路容错**：配置拉取、文件写入、脚本执行等关键步骤均有重试机制；失败后自动回滚，保障数据一致性。
3. **配置回退能力**：个性化配置失效自动回退到公共配置；本地配置文件保留备份，支持手动回滚。
4. **熔断机制**：进程守护具备熔断能力，避免无效重试消耗系统资源。
5. **断连降级**：Nacos 断连自动重连，断连期间沿用本地最后有效配置，不影响本地基础功能。
6. **防僵尸进程**：所有 Shell 子进程均通过 Context 超时控制，超时强制终止，避免资源泄漏。
7. **Shell 输出限流**：stdout/stderr 单流上限 1MB（`MaxShellOutputBytes`），超出截断并标记，防止脚本意外输出大量数据导致 OOM。

### 7.3 安全性设计

1. **全接口鉴权**：所有 HTTP 接口强制鉴权，`/api/v1/exec` 免 HTTP 鉴权但通过 AES 加密保障传输安全。
2. **加密传输**：远程命令内容与执行结果全链路 AES 加密，保障敏感操作安全。
3. **内网部署**：请求透传不做 SSRF 防护，允许代理访问内网任意 http/https 服务（符合内网运维场景预期）。
4. **敏感信息保护**：VictoriaMetrics 鉴权头支持从环境变量读取，避免明文写入配置文件；Shell 执行日志中 stdout/stderr/script 截断到 5KB 预览。
5. **权限控制**：Agent 以运行用户权限执行操作，不主动提权，符合系统权限管控。

### 7.4 兼容性设计

1. **操作系统兼容**：支持 CentOS 7+、Ubuntu 18.04+、Debian 10 + 等主流 Linux 发行版。
2. **架构兼容**：原生支持 amd64、arm64 架构，适配物理机、虚拟机、容器环境。
3. **单文件交付**：纯静态编译，无外部依赖，拷贝即可部署，无需安装任何运行时。

### 7.5 可观测性设计

3. **全场景覆盖**：日志覆盖启动、配置加载、任务执行、健康检查、异常等所有场景。

## 九、部署与运行方案

### 9.1 部署方式

1. **交付物**：单个二进制可执行文件`metric-agent`。
2. **部署步骤**：
   1. 将二进制文件拷贝到目标节点指定目录。
   2. 编写基础配置文件`metricAgent.yml`。
   3. 配置系统服务（如 systemd）实现开机自启。
3. **权限要求**：二进制文件需赋予执行权限；配置文件与目标写入目录需对应读写权限。

### 9.2 运行模式与启动示例

#### 9.2.1 HTTP 服务模式（默认）

```
# 使用默认配置启动
./metric-agent

# 指定配置文件与监听地址
./metric-agent --config=/etc/metric-agent/metricAgent.yml --bind-addr=0.0.0.0:9092
```


#### 9.2.2 指令执行模式

```
# 直接执行脚本
./metric-agent --exec="ls -l /opt"

# 执行脚本文件
./metric-agent --exec-file=/tmp/check.sh

# 使用--分隔符传递参数
./metric-agent --exec="echo" -- hello world
```


### 9.3 运行维护

1. **日志查看**：默认日志路径`./logs/metricAgent.log`，支持通过日志文件排查问题。
2. **配置变更**：Nacos 侧配置变更后自动同步，无需重启 Agent。
3. **进程管理**：推荐使用 systemd 管理，配置重启策略，实现进程异常自动重启。

## 十、风险评估与应对措施

表格

| 风险类型 | 风险描述                | 影响等级 | 应对措施                                                      |
| ---- | ------------------- | ---- | --------------------------------------------------------- |
| 技术风险 | Nacos SDK 与服务端兼容性问题 | 中    | 锁定 v2.3.5 版本，该版本已针对 Nacos 2.x 全系列做兼容性适配，经过生产验证；提前完成集成测试验证 |
| 技术风险 | Shell 执行安全风险，命令注入   | 高    | 1. 所有 HTTP 接口强制鉴权（除 `/api/v1/exec` 免 HTTP 鉴权但依赖 AES 加密）2. Shell 执行日志中 stdout/stderr/script 截断到 5KB，防止敏感信息泄漏 3. Agent 以普通用户运行，限制操作权限 |
| 技术风险 | 子进程泄漏，资源耗尽          | 中    | 所有 Shell 执行均通过 Context 超时控制，超时强制终止；Unix 杀整个进程组，Windows 杀进程树；守护协程定期巡检，避免僵尸进程 |
| 技术风险 | Shell 输出过大导致 OOM      | 中    | 所有 Shell 执行 stdout/stderr 单流上限 1MB（`MaxShellOutputBytes`），超出截断并 Warn 标记 |
| 运维风险 | 配置错误导致启动失败          | 中    | 启动时严格校验配置格式与必填字段，输出精准错误提示；配置变更采用灰度发布                      |
| 运维风险 | Nacos 断连导致配置无法更新    | 低    | 断连期间沿用本地最后有效配置，不影响 Agent 运行；自动重连机制保障快速恢复                  |
